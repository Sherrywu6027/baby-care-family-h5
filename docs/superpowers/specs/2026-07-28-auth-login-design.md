# 宝宝照护记录应用 - 正式登录与家庭恢复设计方案

- 日期：2026-07-28
- 状态：已与用户确认采用“正式登录 + 登录后自动恢复家庭”的第一版方案
- 范围：为现有 H5 / PWA 项目补齐稳定账号体系，解决“清缓存、换设备、重新进入创建页后无法找回原家庭”的问题

---

## 1. 背景

当前项目已经具备家庭协作数据模型：

- `members.auth_user`
- `families.creator_user`
- 大部分 RPC 已经基于 `auth.uid()` 鉴权

但前端当前仍以匿名会话和本地缓存为主：

- `sync.js` 在没有正式会话时自动匿名登录
- `app.js` 用 `onboardingCompleted` 决定是否进入欢迎页
- 本地 `IndexedDB/meta` 一旦丢失，设备就会被当成新用户

因此会出现以下问题：

1. 用户重新打开页面后又进入“创建家庭 / 加入家庭”页
2. 原家庭身份无法稳定恢复
3. 原家庭创建者在丢失本地身份后，前端无法再次证明自己是原创建者

这不是“家庭功能缺失”，而是“身份体系不稳定”。

---

## 2. 目标

本次设计的目标是：

1. 让用户身份脱离“当前设备缓存”，变成可跨设备恢复的正式账号
2. 让同一账号在新设备登录后，能够自动找回原家庭
3. 保持现有家庭、成员、记录、同步模型尽量不重写
4. 允许后续继续扩展为手机号登录或微信登录

本次第一版只解决“稳定登录 + 家庭恢复”，不追求一次做完所有账号治理。

---

## 3. 非目标

本次不包含以下内容：

1. 微信登录
2. 手机号短信验证码登录
3. 管理后台人工找回工具
4. 复杂的老匿名身份自动认领算法
5. 多账号合并
6. 大规模重构 UI 框架

这些能力可以作为后续迭代，但不进入第一版范围。

---

## 4. 方案选择

本次评估了三种路径：

### 方案 A：邮箱 OTP 登录

- 使用 Supabase Auth 邮箱验证码
- 输入邮箱，收验证码，验证后登录
- 开发成本最低
- 最容易快速验证“登录后自动恢复家庭”的主链路

优点：

- 不需要额外短信服务
- 与现有 Supabase 集成最直接
- 风险最低，落地最快

缺点：

- 对家庭长辈用户不如手机号直观

### 方案 B：手机号 OTP 登录

- 用户体验更贴近日常使用
- 更适合长期产品形态

优点：

- 用户理解成本低
- 更适合家人协作产品

缺点：

- 开发和环境配置复杂度更高
- 依赖短信能力

### 方案 C：继续匿名 + 增加设备迁移

- 仍然以匿名身份为主
- 通过家庭码、设备绑定、迁移页面修补恢复问题

优点：

- 表面上改动较少

缺点：

- 核心问题没有真正解决
- 身份仍然依赖设备
- 后续越修越复杂

### 结论

第一版采用方案 A：

- 先上线 `邮箱 OTP 登录`
- 用最小成本把身份从“设备”升级为“账号”
- 后续如有需要，再在同一架构上升级为手机号或微信登录

---

## 5. 核心设计

### 5.1 账号成为身份真相来源

第一版之后，家庭身份的真相来源变为：

- Supabase Auth 当前登录用户
- `members.auth_user`

本地 `IndexedDB/meta` 仍然保留，但只承担：

1. 页面缓存
2. 本地离线数据缓存
3. 最近使用状态保存

本地缓存不再承担“你是谁”这个根职责。

### 5.2 页面访问规则

页面进入规则调整为：

1. 未登录
   - 一律进入 `#/login`

2. 已登录但未加入家庭
   - 进入 `#/welcome`

3. 已登录且已加入家庭
   - 直接进入主页面

4. 已登录且存在待审核加入申请
   - 进入 `#/welcome`
   - 直接显示待审核状态

### 5.3 欢迎页角色变化

现有 `welcome` 页面不再承担“未登录新用户入口”角色，而是改成：

- 已登录但未进入家庭的引导页
- 负责：
  - 创建家庭
  - 输入家庭码申请加入
  - 展示待审核状态

这样可以把“登录”与“进入家庭”拆开，避免逻辑混杂。

---

## 6. 前端结构调整

### 6.1 新增登录页

新增页面：

- `#/login`

第一版登录页流程：

1. 输入邮箱
2. 点击发送验证码
3. 输入验证码
4. 验证成功后建立正式会话
5. 进入恢复流程

页面文案重点应强调：

- 登录后可跨设备找回家庭记录
- 换手机、清缓存后仍可恢复

### 6.2 路由守卫

`app.js` 的启动流程改为优先判断登录态，而不是优先判断 `onboardingCompleted`。

建议逻辑：

1. 启动应用
2. `Sync.init()`
3. 获取认证状态
4. 根据认证状态决定路由：
   - 未登录 -> `login`
   - 已登录 -> 再判断是否已有家庭

`onboardingCompleted` 仍可保留，但只能作为 UI 缓存状态，不能再单独决定是否为“老用户”。

### 6.3 设置页新增账号区

设置页新增“账号”模块：

1. 当前登录邮箱
2. 登录状态
3. 退出登录
4. 重新同步

退出登录后要清理：

- `familyId`
- `familyCode`
- `pendingJoinCode`
- `pendingJoinRequestedAt`
- `onboardingCompleted`
- `authUserId`
- 本地 last sync 状态

但不强制删除本地历史缓存数据；是否清缓存可作为后续能力。

---

## 7. Sync 层设计

### 7.1 `Sync.init()` 角色变化

当前 `Sync.init()` 会在没有 session 时自动匿名登录。

第一版改为：

1. 如果已有正式 session，恢复 session
2. 如果没有正式 session，返回未登录状态
3. 不再默认匿名登录作为主路径

匿名模式如果保留，只能作为未来“纯本地试用模式”的单独入口，不能和家庭共享主链路混用。

### 7.2 新增认证相关能力

建议在 `sync.js` 中新增以下接口：

1. `getAuthState()`
   - 返回：
     - `loggedIn`
     - `user`
     - `email`

2. `sendLoginCode(email)`
   - 发送邮箱 OTP

3. `verifyLoginCode(email, code)`
   - 校验验证码并建立 session

4. `signOut()`
   - 退出登录并清本地身份状态

5. `restoreFamilyContext()`
   - 登录后自动恢复家庭上下文

### 7.3 登录后家庭恢复流程

`restoreFamilyContext()` 的建议流程：

1. 获取当前 `auth.uid()`
2. 查询当前账号是否已属于某个家庭
3. 如果属于家庭：
   - 写入 `familyId`
   - 写入 `familyCode`
   - 写入 `onboardingCompleted = true`
   - 清理 `pendingJoinCode`
   - 执行一次 `sync({ silent: true })`
4. 如果不属于任何家庭：
   - 写入 `onboardingCompleted = false`
   - 跳转 `welcome`

这样，同一账号换设备登录后，不需要重新创建或重新加入家庭。

---

## 8. 后端与数据模型

### 8.1 保持现有成员模型

当前表设计已经适合正式登录：

- `members.auth_user`
- `families.creator_user`
- `current_family()`

本次第一版不建议大改 schema。

### 8.2 建议新增 RPC

建议新增一个轻量 RPC：

#### `get_my_membership()`

返回当前登录用户的家庭归属，例如：

- `family_id`
- `family_code`
- `member_id`
- `role`
- `display_name`
- `is_creator`

用途：

- 登录后快速恢复家庭上下文
- 避免前端直接拼表查询
- 让恢复逻辑集中且可控

### 8.3 可选补充 RPC

第一版可不做，但后续建议补：

#### `list_my_join_requests()`

用于：

- 登录后查看自己待审核的加入申请
- 在 `welcome` 页面更稳定地展示“等待审核”状态

---

## 9. 老用户兼容策略

### 9.1 第一版原则

第一版不强求自动修复所有历史匿名身份，只保证：

1. 新登录用户后续不会再轻易丢身份
2. 仍保留旧数据的设备可继续接入
3. 关联失败时，允许用户重新申请加入家庭

### 9.2 可恢复场景

以下场景可平滑恢复：

1. 用户原设备还在，且本地状态未完全丢失
2. 用户不是创建者，且家庭内还有创建者或其他可操作成员
3. 用户记得家庭码，可重新申请加入

### 9.3 无法完全自动恢复的场景

以下场景前端无法独立解决：

1. 原创建者丢失旧匿名身份
2. 没有任何还能进入原家庭的旧设备
3. 无法证明当前新账号就是原创建者

这类情况只能通过数据库人工修复。

因此第一版必须明确产品提示：

- 登录能解决绝大多数后续恢复问题
- 但对已经丢失匿名身份的历史创建者，不保证自动找回

## 10. UI 流程

### 10.1 首次用户

1. 打开应用
2. 进入登录页
3. 完成邮箱验证码登录
4. 若未加入家庭 -> 进入 welcome
5. 创建家庭或申请加入家庭

### 10.2 已有家庭成员换设备

1. 打开应用
2. 登录同一个邮箱
3. 系统执行 `restoreFamilyContext()`
4. 自动恢复家庭并同步数据
5. 直接进入主页面

### 10.3 已申请加入但待审核

1. 登录后无家庭
2. 查询到待审核申请
3. 进入 welcome
4. 展示“申请处理中”

### 10.4 退出登录

1. 用户在设置页点击退出
2. 清理本地身份上下文
3. 跳回登录页

## 12. 错误处理

第一版至少处理以下错误：

1. 邮箱格式错误
2. 验证码发送失败
3. 验证码错误或过期
4. 登录成功但恢复家庭失败
5. 用户已登录但本地状态残留冲突

错误处理原则：

1. 登录错误在登录页内提示
2. 恢复家庭失败时给出“重新同步 / 去欢迎页”的明确入口
3. 不要让用户卡在空白页

---

## 13. 测试范围

第一版至少覆盖以下验证：

1. 未登录打开应用，自动进入登录页
2. 输入邮箱并完成验证码登录
3. 已在家庭中的账号登录后自动进入原家庭
4. 未加入家庭的账号登录后进入 welcome
5. 有待审核申请的账号登录后能看到待审核状态
6. 设置页退出登录后回到登录页
7. 退出后再次登录同一账号，仍能恢复原家庭

回归验证重点：

1. 现有创建家庭流程不被破坏
2. 现有加入家庭审核流程不被破坏
3. 现有同步流程在正式登录后仍可工作

---

## 14. 风险与约束

主要风险：

1. 现有逻辑大量依赖本地 meta 状态，切换到账号主导后容易出现双真相源问题
2. 原匿名用户历史数据恢复存在边界场景
3. 如果继续保留匿名主路径，会再次把逻辑拉回混乱状态

约束：

1. 第一版必须明确“正式登录是家庭共享主路径”
2. 不做复杂历史认领自动化
3. 恢复逻辑必须集中在 `Sync` 层，不散落到各页面

---

## 15. 实施顺序建议

建议按以下顺序推进：

1. 新增 `get_my_membership()`
2. 新增 `ui-login.js`
3. 改 `sync.js` 认证逻辑，去掉匿名主路径
4. 改 `app.js` 路由守卫
5. 改 `welcome` 与 `settings` 页面
6. 最后做兼容清理与回归测试

---

## 16. 结论

本次问题的根因不是“家庭协作能力不够”，而是“账号身份不稳定”。

第一版最合理的修复方式是：

1. 引入正式登录
2. 以正式账号作为家庭身份真相来源
3. 登录后自动恢复家庭关系
4. 保持现有家庭和同步模型尽量不推倒重来

本次确定采用：

- `Supabase Auth 邮箱 OTP`
- `登录页 + 路由守卫`
- `get_my_membership()`
- `登录后自动恢复家庭`

这是当前成本最低、收益最高、最容易落地的一版。
