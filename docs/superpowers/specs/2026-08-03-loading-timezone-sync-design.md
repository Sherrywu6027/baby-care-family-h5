# 宝宝记录 H5 止血优化设计

- 日期：2026-08-03
- 状态：已与用户确认
- 范围：仅覆盖登录后空白、北京时间分日、家庭协作同步延迟

## 1. 背景

当前 H5 已具备登录、家庭、宝宝、记录、同步等主流程，但存在 3 个直接影响日常使用体验的问题：

1. 注册或登录成功后，首页会出现一段时间空白。
2. 按天统计未统一按中国时区处理，凌晨记录可能落到错误日期。
3. 家庭成员之间的数据同步不够及时，常需要手动刷新或等待较久。

本轮目标是先止血，不做大规模技术重构，不引入新前端框架，不改业务范围，只在现有原生 H5 架构上补齐关键体验。

## 2. 目标

本轮上线后应满足以下结果：

1. 用户登录或注册后，页面不再出现无反馈白屏。
2. 首页、记录页、统计页对同一条记录的日期归属完全一致。
3. 家庭成员新增、编辑、删除记录后，其他成员在正常使用路径下可更快看到更新。
4. 同步状态对用户轻提示，但不打断操作。

## 3. 非目标

本轮明确不做以下内容：

1. 不接入 Supabase Realtime 实时订阅。
2. 不重构为 React、Vue、uni-app、Taro 等框架。
3. 不处理换尿布大便量首页统计。
4. 不处理睡眠时长报表展示。
5. 不处理首页宝宝标签年龄到天。

## 4. 总体策略

采用“本地优先显示、后台静默恢复、统一业务时间口径、轻状态反馈”的方案。

核心原则：

1. 页面先有内容，再变新，不让用户先看空白。
2. 所有按天逻辑统一按北京时间自然日计算。
3. 同步默认自动发生，用户不需要频繁手动点击。
4. 更新后尽量局部刷新，避免整页闪动。

## 5. 方案一：登录后不再白屏

### 5.1 问题定义

当前登录成功后，页面会先进入业务路由，再等待家庭、宝宝、同步上下文恢复，导致主区域短时间没有有效内容。

### 5.2 设计

登录或注册成功后的页面恢复流程调整为：

1. 先检查本地是否存在最近一次有效的家庭、宝宝、今日页数据快照。
2. 若存在快照，立即渲染今日页骨架和最近数据。
3. 若不存在快照，但账号上下文仍在恢复中，则渲染今日页内骨架态。
4. 后台继续恢复登录态、家庭上下文、宝宝列表、今日数据。
5. 若最终确认该账号已有家庭，则直接停留在今日页并更新真实数据。
6. 若最终确认该账号没有家庭，则再进入创建或加入家庭流程。

### 5.3 用户可见效果

1. 不再出现独立白屏。
2. 已有使用历史的用户优先看到上次内容，再无感更新。
3. 新用户首次进入时看到的是今日页骨架，而不是空容器。
4. 已有家庭的用户登录后直接进入今日页，不再掉入“选择家庭”中间页。

### 5.4 实现边界

本轮不新增独立启动页，避免路由层继续复杂化；优先在今日页内部处理骨架态和缓存恢复。

## 6. 方案二：统一按北京时间分日

### 6.1 问题定义

当前代码同时存在以下不同口径：

1. 使用 `toISOString().slice(0, 10)` 取得日期，实质按 UTC 截断。
2. 使用浏览器本地 `Date` 解析 `YYYY-MM-DDT00:00:00` 作为日界。
3. 不同页面分别自己计算“今天”和“某天范围”。

这会导致凌晨记录在首页、记录页、统计页出现分桶不一致。

### 6.2 设计

新增统一的业务时间工具层，所有与“按天”有关的逻辑必须调用同一套方法，禁止页面自行拼接日期边界。

统一口径如下：

1. 业务时区固定为 `Asia/Shanghai`。
2. 业务自然日范围固定为北京时间 `00:00:00` 到 `23:59:59.999`。
3. “今天”“近 7 天”“某记录属于哪一天”“表单默认日期”均按该口径处理。

### 6.3 覆盖范围

至少统一以下场景：

1. 首页今日统计。
2. 记录页按天筛选。
3. 统计页日维度与近 7 天汇总。
4. 新建记录时默认日期。
5. 保存记录时从日期和时间拼装时间戳的逻辑。

### 6.4 结果要求

1. 用户北京时间凌晨 `00:10` 新增的记录，必须计入当天。
2. 用户北京时间 `23:50` 新增的记录，必须仍计入当天。
3. 首页、记录页、统计页对同一记录的日期归属必须一致。

## 7. 方案三：同步改成“秒开 + 静默刷新”

### 7.1 问题定义

当前同步更多依赖页面进入时的有限触发和用户手动动作，无法满足家庭协作场景下的数据新鲜度需求。

### 7.2 设计

同步策略拆成三层：

1. 页面打开时先读本地快照，立即渲染。
2. 用户新增、编辑、删除后，立即触发一次静默同步。
3. 页面从后台回到前台时，自动触发一次补拉同步。

前台恢复场景包括但不限于：

1. `visibilitychange`
2. `focus`
3. `pageshow`

### 7.3 同步状态提示

页面增加轻量同步状态提示，不弹窗、不阻断，状态文案限定为：

1. `刚刚更新`
2. `同步中`
3. `离线，稍后自动同步`
4. `同步失败，可稍后重试`

### 7.4 刷新策略

同步完成后优先局部刷新当前受影响模块，不默认整页重渲染。

例如：

1. 今日页只更新汇总卡片、进行中计时、最近记录区块。
2. 记录页只更新当前日期列表。
3. 设置页只更新家庭成员、家庭信息等对应模块。

### 7.5 用户体验要求

1. 用户打开页面时可先看到最近一次缓存数据。
2. 家庭成员 A 保存后，成员 B 重新切回页面时能较快看到更新。
3. 弱网或离线时仍可继续本地使用，并看到轻提示。

## 8. 数据与状态设计

### 8.1 本地快照

新增或完善页面级快照缓存，至少覆盖：

1. 当前家庭上下文。
2. 当前选中宝宝。
3. 最近一次今日页可展示数据。
4. 最近一次同步时间和同步状态。

### 8.2 状态优先级

页面渲染优先级统一为：

1. 先用本地可用快照渲染。
2. 再进入后台恢复和同步。
3. 云端数据返回后覆盖本地展示。
4. 若同步失败，保留已显示内容，仅更新轻提示状态。

## 9. 错误处理

### 9.1 登录后恢复失败

1. 若本地已有快照，则继续展示快照并提示稍后重试。
2. 若本地无快照，则显示今日页骨架和恢复中状态，不显示空白容器。

### 9.2 同步失败

1. 不清空当前页面内容。
2. 提示 `同步失败，可稍后重试`。
3. 下次保存、回前台、网络恢复时继续重试。

### 9.3 时区异常

即使设备系统时区不是中国时区，业务分日仍强制按北京时间口径执行。

## 10. 测试重点

本轮至少覆盖以下验收场景：

1. 新用户注册后进入首页，不出现白屏。
2. 老用户登录后，如已有家庭，直接进入今日页。
3. 无本地快照时，页面显示今日页骨架，不显示空白区域。
4. 北京时间凌晨新增记录后，首页、记录页、统计页归属一致。
5. 家庭成员 A 新增记录后，成员 B 切回页面时能自动看到更新。
6. 离线情况下页面仍可继续记录，并显示离线同步提示。
7. 同步失败时页面内容不丢失，仅提示状态变化。

## 11. 实施顺序建议

建议按以下顺序落地，减少互相干扰：

1. 先抽离统一时间工具层并替换现有分日逻辑。
2. 再补登录恢复态、今日页骨架态、本地快照渲染。
3. 最后补保存后同步、前台恢复同步、轻状态提示和局部刷新。

## 12. 风险与取舍

### 12.1 保留现有原生架构

优点是本轮可以快速止血，避免大范围重构。  
代价是后续如果继续深做复杂功能，维护成本仍会逐步上升。

### 12.2 不上 Realtime

优点是复杂度低，短期更稳。  
代价是同步不是严格实时，而是“足够快的自动刷新”。

### 12.3 缓存优先显示

优点是打开更丝滑。  
代价是极短时间内可能先看到旧数据，但会被静默刷新覆盖，因此需要轻状态提示辅助理解。
