# 宝宝照护记录应用 - 家庭协同版设计方案
- 日期：2026-07-27
- 状态：已与用户确认方向 B，采用“离线优先 + 增量上云”方案
- 范围：在现有 H5 / PWA 项目基础上，分 3 期完成真实多人共享、基础冲突处理与产品化协同能力

---

## 1. 目标

把当前“本地记录工具”升级为“家庭共享记录工具”，支持同一家庭内多台手机查看和维护同一份宝宝照护数据。

本次设计覆盖 3 个阶段目标：

1. 第 1 期：真实多人共享可用
2. 第 2 期：补齐冲突处理和同步可靠性
3. 第 3 期：补齐成员角色、邀请加入、首屏拉取、失败恢复等产品化能力

当前确认的同步时效要求为：

- 第 1 期只要求“进入页面或手动同步后可看到最新数据”
- 暂不要求秒级自动同步
- 暂不要求计时中的实时跨端状态同步

---

## 2. 非目标

本设计当前不覆盖以下内容：

- 小程序端立刻重构或迁移
- 实时 WebSocket / Realtime 秒级同步
- 多人同时编辑同一条记录时的可视化 diff 对比
- 计时中的跨端接力或远程控制
- SaaS 化租户、计费和后台管理

---

## 3. 推荐方案

采用“离线优先 + 本地先写 + 增量上云”的架构。

核心原则：

- UI 仍然只依赖本地数据源，保证操作即时响应
- 所有新增、编辑、删除先成功写入 IndexedDB
- 同步器负责把本地变更推送到 Supabase，再把云端增量拉回本地
- Supabase 作为家庭共享的权威后端
- 本地库作为前端运行时事实源和离线缓存

不采用“云端优先”的原因：

- 现有代码中 `UI -> DB -> Calc` 结构已经稳定
- 直接改成云端直写会扩大改造面
- 会把多人协同改造和架构迁移绑在一起，风险过高

不采用“双写过渡”的原因：

- 会引入额外一致性问题
- 后续第 2、3 期更难收口

4. 数据与同步层
   - `db.js`

### 5.2 职责边界

`DB` 负责：

- 本地持久化
- 本地查询
- 待同步状态维护
- 本地合并云端数据

`Sync` 负责：

- Supabase 客户端初始化
- 认证与家庭上下文建立
- 推送本地待同步变更
- 拉取云端增量
- 记录同步游标、错误和状态

`UI` 不直接读写 Supabase，只通过 `DB` 和 `Sync` 协作。

## 6. 数据模型设计

### 6.1 主键策略

本地生成的 `babies.id` 和 `events.id` 直接作为云端主键使用。

理由：

- 避免维护本地 ID / 云端 ID 映射表
- `update` / `delete` 可以天然对齐
- 小程序后续复用协议更简单
- 导入导出与多端合并更容易做幂等

### 6.2 本地与云端统一字段

建议对 `babies` 和 `events` 至少统一以下字段：

- `id`
- `family_id`
- `created_at`
- `updated_at`
- `deleted_at`
- `sync_status`
- `client_id`
- `last_synced_at`

其中：

- `deleted_at`
  说明软删除时间，非空代表逻辑删除
- `sync_status`
  可取值：
  - `pending_create`
  - `pending_update`
  - `pending_delete`
  - `synced`
  - `conflict`
- `client_id`
  标识当前设备
- `last_synced_at`
  标识本地该条记录最后一次与云端对齐时间

第 2 期可选增加：

- `version` 或 `updated_seq`

第 1 期先只依赖 `updated_at` 即可。

### 6.3 删除策略

本次设计统一采用软删除：

- 本地删除时，不立即物理删除
- 写入 `deleted_at` 并标记 `pending_delete`
- 同步到云端后，对其他设备可见
- UI 查询默认过滤 `deleted_at is not null` 的记录
- 是否做本地物理清理，留待后续后台清理策略处理

## 7. 同步闭环

### 7.1 触发时机

第 1 期同步触发点：

- 应用启动后
- 用户进入首页或设置页
- 用户手动点击“立即同步”
- 浏览器 `online` 事件触发后

### 7.2 同步顺序

每次执行 `Sync.sync()` 时，固定顺序如下：

1. 确保 Supabase 客户端和会话已就绪
2. 确保当前设备已有 `family_id`
3. 上传本地待同步变更
4. 拉取云端自上次同步后的增量
5. 合并到本地库
6. 更新 `last_sync_at`、状态和错误信息

### 7.3 上传策略

本地新增：

- `pending_create`
- 云端执行 upsert

本地编辑：

- `pending_update`
- 云端按主键 upsert

本地删除：

- `pending_delete`
- 云端只更新 `deleted_at`

### 7.4 拉取策略

第 1 期采用基于 `updated_at` 的增量拉取：

- 拉取 `updated_at > last_sync_at` 的宝宝和事件
- 拉取结果按 `id` 写回本地
- 如果本地不存在则插入
- 如果本地存在且本地不是待同步状态，则直接覆盖
- 如果本地也是待同步状态，则进入冲突判定

---

## 8. 冲突策略

### 8.1 第 1 期

第 1 期使用最小可用策略：

- 默认按 `updated_at` 晚者覆盖
- 若本地和云端同时有未对齐修改，则本地标记 `conflict`
- UI 至少在设置页显示“最近同步存在冲突”

### 8.2 第 2 期

第 2 期增强策略：

- 新增冲突分类：`create/update/delete`
- `create` 冲突视为幂等重复提交
- `update` 冲突仍以晚者覆盖为默认规则
- `delete` 冲突删除优先
- `baby` 档案也按晚者覆盖

### 8.3 不纳入冲突同步的对象

计时中的运行态不跨端同步：

- `Timer` 状态继续只保存在本地 `localStorage`
- 仅在“结束计时并生成 event”后进入同步链

这样可以避免第 1 期引入复杂的实时状态广播。

## 11. 迁移到小程序的策略

当前不建议为小程序立即迁框架。

更合理的路径是：

1. 先把 H5 的业务规则、同步协议和数据模型稳定下来
2. 把可复用逻辑尽量压到“非 DOM 依赖”的层
3. 后续单独做小程序壳，复用规则与同步协议

推荐的中间态：

- H5 继续作为主工程
- 小程序后续单独实现 UI
- 优先复用：
  - 数据模型
  - 统计逻辑
  - 同步协议
  - 冲突规则

如果未来确实要统一跨端框架，再考虑：

- `Taro`
- `uni-app`

但迁移时机应放在家庭协同版稳定之后，而不是现在。

原因：

- 当前项目是原生 JS，不是 React / Vue 工程
- 现在同时做“同步闭环 + 技术栈迁移”风险太高
- 先稳住业务层，后换壳更可控

## 13. 风险与约束

主要风险：

- 现有本地删除是物理删除，改软删除会影响既有查询逻辑
- `updated_at` 作为唯一冲突依据时，依赖设备时间基本可信
- 现有页面代码较集中，若不克制范围，容易把同步逻辑散落到 UI

对应约束：

- 同步逻辑必须集中到 `sync.js`
- 本地合并逻辑必须集中到 `db.js`
- UI 页面只消费结果，不直接处理云端差异

---

## 14. 实施建议

建议按以下顺序推进：

1. 先改 `schema.sql` 和 `db.js`，把字段和本地状态打平
2. 再重写 `sync.js` 的家庭创建、加入和 push / pull 闭环
3. 接着补 `ui-settings.js` 的同步状态和手动同步入口
4. 最后在 `app.js` 里加轻量自动触发

这样能把影响面控制在数据层优先，减少 UI 回归风险。

---

## 15. 结论

本项目做“家庭协同版”的正确路径，不是先迁技术栈，而是先把现有 H5 的离线优先架构补成真正可共享的多端同步产品。

设计结论如下：

- 采用“离线优先 + 增量上云”方案
- 本地 ID 直接作为云端主键
- 第 1 期只要求手动或进页面可同步
- 计时中的运行态不跨端同步
- 先完成 3 期协同能力，再考虑小程序壳或跨端框架迁移
